I broke ID-JAG five ways (so you don't have to)

If you work in identity, you've seen the hype: the ID-JAG — Identity Assertion JWT Authorization Grant — is the new OAuth grant that lets AI agents act on a user's behalf without consent-screen hell. Okta's XAA sandbox will show you the happy path in 30 seconds. User signs in, IdP issues the grant, the grant becomes an access token, the API gets called. Clean.

But the happy path doesn't teach you where enforcement lives. And "where does this die when it breaks" is the question you'll actually ask at 11pm during an integration. So I built a Failure Gallery — five interactive scenarios, zero setup — and ran each one to watch the denial land.

The five failures

1. The expired assertion

Present the grant ten minutes after issuance. It's valid for five. The resource server's exp check kills it. Short lifetimes are the point: a stolen grant is useful for minutes, not months — and the ID-JAG exchange issues no refresh token to extend it.

2. The wrong audience

Mint the grant for the calendar API, present it to the docs API. Dies on the aud check. Audience binding means a stolen grant can't be redirected — it's only valid exactly where it was meant to go.

3. The overreach

Ask for admin:write when enterprise policy allows docs:read. This one never even becomes a token: the IdP refuses to issue. This is the XAA difference in one scenario — the enterprise policy decides, not the user clicking "allow." Overreach dies before a token ever exists.

4. The tampered signature

Flip a scope claim mid-flight, from docs:read to admin:write. The resource server verifies the signature against the IdP's keys — mismatch, denied. The grant is tamper-evident, and the resource server trusts the IdP's keys, never the presenter.

5. The replay

Capture a perfectly valid grant and play it twice. The second presentation dies on single-use jti tracking. Intercepting a grant buys the attacker nothing.

The pattern that matters

Enforcement lives in two places: the IdP at issuance (policy decisions — who and what is allowed) and the resource server at exchange (cryptographic validation — is this grant genuine, fresh, and meant for me). Most "why did my flow fail" debugging sessions end the moment you internalize that split. Ask first: did we fail to get a grant, or fail to spend one? The answer tells you which half to investigate.

Learn the hard way, teach the easy way

The gallery is the zero-setup distillation. In parallel I'm working through the full Kubernetes-based ID-JAG tutorial — real infrastructure, real failures. Every scenario above will eventually be a failure I personally caused on real infra. That's the philosophy: suffer through the hard version so the easy version is honest.
